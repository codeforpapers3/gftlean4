# GFTLean4

Lean 4 formalization accompanying the SBMF 2026 paper:

**Formal Semantics and Machine-Checked Metatheory for General Fault
Trees in Lean 4**

This repository provides an executable semantic framework and
machine-checked metatheory for general fault trees in Lean 4. The
formalized gate language supports **AND, OR, NOT, NAND, and NOR** gates.
The development also identifies a positive AND/OR fragment, establishes
its monotonicity, and demonstrates reuse of the generic theory through a
satellite solar-array mechanical-system fault-tree case study.

## Scope of the Formalization

The repository contains:

-   a generic syntax for general fault trees over an arbitrary
    basic-event type;
-   structural functions and properties for fault trees;
-   structural well-formedness and positivity predicates;
-   executable Boolean semantics;
-   semantic equivalence and cut-set satisfaction;
-   Boolean-algebraic laws;
-   monotonicity theory;
-   a proof-carrying positive-tree interface;
-   equivalence-preservation results; and
-   executable and machine-checked solar-array case studies.

In this repository, **general fault trees** refers specifically to the
language generated by AND, OR, NOT, NAND, and NOR gates. The development
does not claim to cover all static or dynamic fault-tree operators.

### Semantic equivalence

`SemEquiv` states that two fault trees evaluate identically for every
failed-event configuration. It is shown to be reflexive, symmetric, and
transitive:

``` lean
SemEquiv.refl
SemEquiv.symm
SemEquiv.trans
```

Additional results connect equivalence with evaluation, cut-set
satisfaction, and monotonicity:

``` lean
SemEquiv.eval_eq
SemEquiv.isCutSet_iff
SemEquiv.monotone_of_left
SemEquiv.monotone_of_right
SemEquiv.monotone_iff
```

### Monotonicity of positive fault trees

The central monotonicity result is:

``` lean
positive_monotone
```

It establishes that every fault tree satisfying `Positive` is
semantically monotone with respect to failed-event-set inclusion.

The development also contains explicit non-monotonicity results for
negative gate behavior, including:

``` lean
nand_basic_not_monotone
nor_basic_not_monotone
```

These results demonstrate why monotonicity is associated with the
positive AND/OR fragment rather than the unrestricted general language.

### Proof-carrying positive trees

`GeneralPositive.lean` defines:

``` lean
structure PositiveTree
```

A `PositiveTree Event` packages a general fault tree together with a
proof that it belongs to the positive fragment. The function

``` lean
PositiveTree.ofGeneral
```

constructs such an object from a `GFTree` and a proof of `Positive`.

This interface allows downstream developments to work directly with
fault trees whose positivity invariant is already certified.

## Solar-Array Case Study

`SolarArrayCaseStudy.lean` formalizes two related fault-tree models
derived from the satellite solar-array mechanical-system case study used
in the paper:

1.  the hinge subsystem; and
2.  the complete mechanical-system fault tree.

The hinge model is represented by:

``` lean
HingeFailure
```

and the complete mechanical-system top event by:

``` lean
SolarArrayFailure
```

Both models reuse the generic syntax, structural theory, executable
semantics, positivity definition, and monotonicity theorem. No
case-study-specific semantic evaluator or model-specific monotonicity
theory is introduced.

The following properties are machine checked:

``` lean
HingeFailure_wellFormed
HingeFailure_positive
HingeFailure_monotone

SolarArrayFailure_wellFormed
SolarArrayFailure_positive
SolarArrayFailure_monotone
```

The file also contains executable and theorem-level checks for
representative event configurations, including:

``` lean
G1_triggers_SolarArrayFailure
G15_triggers_SolarArrayFailure
G32_triggers_SolarArrayFailure
empty_does_not_trigger_SolarArrayFailure
```

### Structural statistics

The numerical structural statistics reported for the case study are
available through executable `#eval` commands and are additionally
certified by named Lean theorems.

For the hinge subsystem:

``` lean
HingeFailure_structural_statistics
```

certifies:

-   size = 26;
-   height = 6;
-   gate count = 12;
-   leaf count = 14;
-   maximum degree = 2; and
-   number of distinct basic events = 8.

For the complete mechanical system:

``` lean
SolarArrayFailure_structural_statistics
```

certifies:

-   size = 51;
-   height = 6;
-   gate count = 18;
-   leaf count = 33;
-   maximum degree = 5; and
-   number of distinct basic events = 33.

Thus, the corresponding reported structural values are not only
executable outputs but are also stated as machine-checked propositions
in Lean.

### Note on the `T8` reconstruction

The published source used for the case study contains an ambiguity
concerning intermediate event `T8`: the tabular description associates
`T8` with `G15`, whereas the fault-tree figure depicts additional
descendants. The Lean case-study file documents this issue explicitly
and encodes the reconstruction used in the paper as:

``` lean
SA_T8
```

The rationale is recorded directly next to the definition in
`SolarArrayCaseStudy.lean` so that the modeling decision is transparent
and reproducible.

Clone the repository and enter the project directory:

``` bash
git clone https://github.com/codeforpapers3/gftlean4.git
cd gftlean4
```

Then build the complete formalization:

``` bash
lake build
```

On a fresh clone, Lake will obtain the dependencies specified by the
project configuration. The build checks all imported definitions and
machine-checked proofs in the library.

``` text
GFTLean4.lean
```

## Scope and Limitations

This artifact formalizes a Boolean semantic foundation for fault trees
with AND, OR, NOT, NAND, and NOR gates. It does **not** currently
provide:

-   quantitative failure probabilities or reliability measures;
-   probability-distribution models;
-   automated cut-set generation or minimal-cut-set computation;
-   dynamic fault-tree gates such as PAND, SPARE, or FDEP;
-   temporal fault-tree semantics; or
-   empirical validation or certification of a physical satellite
    system.

`CutSet Event` is used as the type of a finite failed-event
configuration supplied to the executable semantics. Whether such a
configuration actually triggers a fault tree is expressed separately by
`IsCutSet`.

The solar-array proofs establish properties of the **Lean reconstruction
of the published fault-tree models**. They should not be interpreted as
empirical validation or certification of the underlying physical
spacecraft or deployment mechanism.

The positive-fragment monotonicity theorem applies to fault trees
satisfying the formal `Positive` predicate. Structural validity is
represented separately by `WellFormed`.

## Reproducibility Checklist

A reviewer can reproduce the principal artifact checks as follows:

1.  clone the repository;
2.  verify that the toolchain is `leanprover/lean4:v4.34.0-rc1`;
3.  run `lake build`;
4.  inspect `GeneralSemantics.lean` for the executable semantics;
5.  inspect `GeneralMonotonicity.lean` for `positive_monotone`;
6.  inspect `GeneralPositive.lean` for the proof-carrying positive-tree
    interface;
7.  inspect `SolarArrayCaseStudy.lean` for the two case-study models and
    their proofs; and
8.  inspect the `#eval` commands and the two `*_structural_statistics`
    theorems for the reported structural results.

A successful `lake build` checks the complete imported formalization.
